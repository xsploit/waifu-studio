# Discord adapter work in progress

2026-10-22. An **experimental receive-only native bot worker** now exists at `assets/extensions/discord-live`, launched with `--discord-extension`. It is not in the Add menu and has not been validated against the Discord service. There is no browser bot sign-in, outgoing message path or call transport. Do not enter a Discord token into another integration.

## Implemented message boundary

`discord_messages::ChannelFilter` decodes bounded, decompressed JSON Gateway packets supplied by a future authenticated bot worker. It is pure and performs no I/O. Exactly one configured server and channel are allowed. Direct messages, other channels (including threads with different IDs), bot/webhook messages, system messages, content-less messages and non-create events produce no candidate. Ordinary messages and replies preserve their original content, including whitespace and Unicode. Attachments and embeds are not fetched or converted into text.

Candidates use the existing host `ChatMessage` type. Their source ID qualifies the original message ID with the Discord server and channel IDs. Author identity is the Discord user ID; display-name preference is server nickname, global name, then username. Invalid identities or names, malformed packets, more than 64 KiB of decompressed JSON, and text outside the host's 2048-byte limit are rejected. Text is never silently shortened or summarized. Decoder errors are fixed diagnostics without external content. The Gateway policy rejects individual invalid/oversized chat messages, advances its dispatch checkpoint, and continues the session; chat content cannot itself force authentication to restart.

The decoder does not authenticate a packet, grant target authority, deduplicate or deliver it. The transport must authenticate the bot Gateway, bound frames and decompression before decoding, and submit candidates through the supported `chat.offer` action with the current host target and granted message capability. Existing intake then owns expiry, deduplication, optional selection and external attribution. An accepted offer is not proof of a reply or speech. Edits/deletions currently produce no mutation of earlier chat; this behavior must be visible in the eventual setup guide.

## Implemented connection policy

`discord_gateway::Gateway` is a pure state machine for a future socket worker. It bounds Hello/authentication waits, schedules jittered heartbeats, requires ACKs, and emits explicit reconnect/stop effects. Extra server-requested heartbeats cannot postpone an outstanding ACK deadline; unsolicited ACKs cannot acknowledge a heartbeat only now being scheduled. Monotonic caller time prevents backward clock samples from extending deadlines.

Validated bot READY data retains a session and an allowlisted Discord WSS resume endpoint. Recoverable disconnects resume from the last admitted dispatch sequence. Invalid/expired sessions clear that checkpoint; fatal authentication, intent or shard failures stop instead of retrying forever. Replayed dispatches can be decoded during resume before RESUMED arrives; repeated/older sequences are suppressed. A resume checkpoint is local decoding evidence, not host delivery evidence.

Effects contain no token. The socket worker must attach its private credential only when writing Identify/Resume, close on policy errors, honor minimum reconnect delays with jitter, enforce identify/session-start limits, and discard socket effects on cancellation. It must distinguish transport write failure from an emitted policy effect. None of these pure tests establishes a connection or proves Discord service compatibility.

## Implemented host bridge policy

`discord_host::configured_channel` requires explicit saved numeric server/channel IDs. `HostBridge` consumes a validated extension handshake and emits ordinary versioned `chat.offer` action envelopes. It waits for loaded-avatar target authority and a message-delivery grant. Candidates capture the original target; switching or clearing the target discards queued/in-flight work without assigning it to another avatar.

The bridge holds at most 16 queued plus in-flight messages, one outstanding action, a 15-second original deadline, a 10-second result deadline and 256 source IDs retained for 60 seconds. Dedup survives avatar changes. A full ID cache rejects new input until retention expires rather than evicting replay protection. Only a matching explicit Busy refusal permits a retry: at most three attempts, at least one second apart, within the original deadline. Success, other failures and uncertain timeout/write outcomes are never automatically replayed. Action IDs/sequences advance per attempt.

Host session/process changes and malformed host envelopes stop the bridge. Old host sequences and unrelated results cannot retarget or resolve its outstanding action. Host shutdown is sticky; host EOF, output failure and cancellation must invoke `stop()` before any further transport work. Emitting an action is not proof of writing it, and host acceptance is not proof of speech. The native worker wires this bridge to host JSONL and the Gateway policy. Chat-to-host conversion is tested in-process and over real localhost WebSockets through the production session loop. The offline replay now reaches a recording host offer sink through an installed supervised child; live-worker service delivery and actual conversation/history acceptance remain unverified.

## Next transport work

The worker loads a private `bot_token` credential and explicit `guild_id` / `channel_id` settings from the existing supervised extension environment. It requires observation and external-message grants. The package uses Python3 only to launch the native executable; it installs disabled with no grants. No secret belongs in plain settings. Discord Developer Mode can provide numeric IDs; an authorized bot needs access to the channel and the Message Content intent. Service-side permission/intents acceptance remains unverified.

The worker discovers the Gateway over bounded authenticated HTTPS with redirects disabled and an absolute request/body deadline, validates the endpoint and session-start allowance, and uses the existing TLS/proxy WebSocket helper with 64KiB frame/message bounds. It requests JSON without compression and rejects binary frames. It supports one shard only and stops for multi-shard discovery. Each Identify observes a five-second per-worker floor plus a shared per-user reservation; an exhausted service session-start allowance waits for reset. Credentials are sent only in private service auth/control packets. Error text is fixed and never includes response bodies, URLs with credentials, tokens or chat text.

Host input has a bounded32-message queue and out-of-band EOF/error/overflow flags. It is polled before service effects and host output, during reconnect waits, and before/after bounded connection/discovery operations. Shutdown takes precedence over late operation success or failure, and a late connected socket is dropped before authentication. Supervisor termination remains the boundary for cancellation during a blocked OS/network operation; this is not an instantaneous network-abort guarantee. Reconnect attempts have capped exponential delays and an eight-failure ceiling, reset only after60 seconds of healthy session activity. Failed/uncertain control writes stop rather than automatically resending credentials on that socket. HTTP discovery failures also stop for explicit restart.

Five real localhost WebSocket fixtures now exercise fragmented Hello, Identify, READY, exact chat-to-host JSONL output, shutdown/EOF while a socket is idle, missed heartbeat ACK, fatal authentication close, binary-frame rejection, and reconnect/resume with duplicate replay suppression. They call the same session loop as production, use synthetic credentials and never connect to Discord. Shutdown immediately returns after app.stopping rather than reading the input channel again. These fixtures do not verify remote TLS/discovery, cancellation during DNS/connect/HTTPS, all session-start scenarios, or actual installed-host delivery. Complete the remaining service and installed-delivery checks before exposing the live Discord adapter in Add. The current private CLI failure tests never supply a token and terminate before networking. Live account tests remain prohibited by the offline-only work preference. Normal supervised Linux workers now share an Identify admission reservation across installations/profiles under the same OS account. Other apps, OS users and hosts are outside that coordination scope; Discord remains authoritative for actual service limits.

Outgoing channel replies need their own opt-in, routing and feedback-loop contract.

Voice remains a separate remaining milestone: receive participant audio, configured ASR, conversation ownership, configured speech output, correct call routing, mute/stop, feedback prevention and disconnect recovery. No Discord call/media support or live service acceptance is established by decoder tests.

### Inbound audio boundary (not connected yet)

`discord_audio::Utterance` accepts ordered 20ms mono 16kHz PCM16 frames for one participant and one call/target generation. It produces a bounded WAV for the existing `listen::transcribe_wav` adapter, without capturing the microphone or calling a provider. Duplicate/gapped frames, wrong participants, stale generations and malformed frames are rejected without partial append. Cancellation is sticky; exceeding thirty seconds discards the turn instead of transcribing a truncated utterance. The caller must cancel on disconnect, mute or target replacement and recheck authority before admitting any eventual transcript.

The collector is now connected to the application media sink; Discord call transport remains absent. Decryption, Opus decoding/resampling, participant arbitration/endpointing, echo prevention, ASR job supervision, external transcript attribution, outgoing speech and playback receipts remain required. Do not send raw media through existing metadata events or claim call support from collector tests.

The experimental API1 `audio.input` action now carries an `input` object with a `phase`: `start` includes `turn_id`, `participant_id`, and `participant_name`; `frame` includes `turn_id`, zero-based `frame_sequence` and exactly320 signed PCM16 samples (mono16kHz/20ms); `finish` and `cancel` include `turn_id`. Frame sequences are below1500. Normal action envelope session/process/target/sequence checks apply to each record. Both `audio.transcribe` and `message.deliver` grants are required at host execution. No paths, URLs or device names are accepted. A record acknowledgement means admission only, not successful transcription or persisted conversation. The application implements `ExternalMessageSink::audio_input` for authorized persistent installed sources, forwarding bounded turns to configured ASR and attributed incoming chat. No bundled package requests audio yet. Do not treat this provisional vocabulary as a published stable media API.

`Utterance::transcribe` now calls the existing configured ASR adapter directly as a blocking worker operation, accepting the existing session credential. It retains participant and generation in a distinct `ParticipantTranscript`; it does not touch the microphone composer, history or memory. Caller cancellation must include call/target/service/permission revisions. Checks before assembly, before provider work and after either provider outcome suppress revoked results. They do not interrupt a blocked network operation or replace final host admission. The application now schedules one ASR job and offers validated recognized text through attributed incoming chat; the installed-process media fixture now reaches persisted external history; Discord transport acceptance remains open. Offline injected-provider tests check attribution and cancellation without contacting a service.

`extension_audio::AudioTurns` now provides the host turn store for those records: at most four concurrent turns, one per source session, each bound to the exact host session/process/target/origin/revision. Start freezes participant metadata. Finish consumes the collector once into `ReadyAudio`, retaining the route and participant alongside its WAV. Ordering failure discards the whole turn. Active turns expire after35 seconds; callers must reconcile every frame against current authorized routes. A bounded64-entry replay reservation rejects reuse for60 seconds and refuses new starts while full instead of evicting unexpired identities. Cancellation and route revocation preserve those reservations. The application sink uses this store and owns at most one pending worker/result, with per-frame route and configuration checks.

`extension_audio_job::AsrPool` now provides one process-wide active extension-ASR slot. Reserve it before consuming Finish; a Busy refusal must leave the turn untouched. `AsrPermit::start` moves the completed audio into a named worker and uses the existing ASR configuration/session key. Its one-result channel retains external route/turn/participant identity, with no composer/history writes. Cancellation and Drop suppress publication; the worker retains its permit until actual exit, even when its HTTP operation is blocked. Final host route/configuration/grant checks remain mandatory. Provider failures become fixed errors. The application now owns one pending job/result and reconciles source, target, service and credential changes before polling; the pool alone does not bound arbitrary caller-retained completed job handles. No service call is made by the injected-worker tests.

Current transport research: [Discord requires DAVE support for third-party voice applications](https://support.discord.com/hc/en-us/articles/38025123604631-Minimum-Client-Version-Requirements-for-Voice-Chat). The [discord.js voice guide](https://discordjs.guide/voice) documents its DAVE dependency; its [maintained voice README](https://github.com/discordjs/discord.js/blob/main/packages/voice/README.md) warns that audio receive is undocumented by Discord and stable support is not guaranteed. Use a bot/application transport with current encryption support; the local demo's uploaded Ogg voice messages are not a call transport.


## Try Discord intake offline

Choose **Extensions → Add… → Examples → Discord replay (offline)**. Open its **Permissions** and allow observation and external messages, then enable it and load a character. Python3 launches the native replay; it reads no credential file and opens no service connection. The fixture offers one original synthetic message through the same chunked intake as live messages. Your host incoming-reply settings still determine whether accepted messages can call configured chat/voice models. Leave replies off for a context-only check.

The replay waits for loaded-avatar authority and runs once per explicit process start. Duplicate fixture packets, another channel and a bot message are filtered. Changing avatars does not repeat or transfer the old event. **Advanced → Restart** generates a new synthetic event ID; duplicates within that start retain one identity. Disable stops the process. Busy retries retain the original target/deadline and cancel on avatar change.

Two Linux installed-process tests cover store installation, disabled/no-grant defaults, supervision, the unchanged package launcher, native replay CLI, host-provided attribution and recording offer-sink acceptance, explicit restart, disable and cancellation of a Busy retry. The test-only launcher shim supplies the real native app path because the supervisor's current executable is otherwise the Rust test harness. No production endpoint override is introduced. These checks execute no chat/voice models, persist no conversation and establish no rendered reaction or live Discord compatibility.


## Shared Identify admission (Linux)

All supervised workers use the default per-user Waifu Studio data directory's `discord-identify/identify.lock`, including workers launched from separate profile directories. It stores only a schema version, kernel boot UUID and next eligible boot-clock millisecond. No bot token, account ID or message is written. The directory is owner-only; the file must be a private owned regular file with one link, and symlinked lock files are rejected.

A nonblocking OS lock protects each short read/reserve/write. Before an Identify write, the worker persists and syncs a five-second reservation. Contention returns a wait decision; the socket closes and the ordinary cancellable reconnect wait runs. Cancellation and uncertain writes do not refund reservations. Resume does not reserve an Identify slot. The Linux boot clock includes suspend and is independent of wall-clock changes. A new boot waits until five seconds of uptime, even with no saved file; corrupt or inconsistent state fails closed.

This deliberately serializes Identify admissions across all this app's bot tokens for one OS account, which is more conservative than per-bot/shard limits. It coordinates client admission attempts, not remote receipt/processing time or other applications. Service discovery still checks Discord's remaining session-start allowance and single-shard requirement. Native Windows/macOS coordination and live service acceptance remain open. Offline replay does not open this coordination directory.


## Offline startup boundary checks

Local fake HTTP tests use the production discovery builder/parser with synthetic bot credentials. They verify header shape, valid metadata, disabled redirects (including no request to the redirect target), fixed diagnostics without response/token text, a64KiB response bound, and an absolute request/body deadline under a slow-drip response. The blocking client timeout alone resets on reads; the worker now also sets an eight-second request deadline. The short-deadline fixture failed before that fix and passes after it.

The same startup wrapper is used around discovery and the WebSocket connector. It checks host state before and after an operation, gives shutdown precedence over a late HTTP result, and drops late returned resources before continuation. Tests cover EOF before work, EOF after successful/error discovery, input failure during discovery, and disposal of a late returned connection-like value. These are boundary checks. They do not interrupt an OS call internally or establish DNS/TLS handshake cancellation on a real connection. The supervisor remains responsible for terminating a blocked worker; live TLS/service and blocking-stage fault acceptance remain open. Production discovery endpoints are fixed; only private tests supply alternate endpoints, and no runtime override is exposed.


## Supervised blocked-startup fixtures (Linux)

Two exact child-harness tests now run the production discovery request helper and proxy-aware WebSocket connector under the real `ProcessHandle` supervisor. Local peers deliberately withhold HTTP response headers or TLS ServerHello after receiving a real ClientHello. Another child uses reqwest's custom resolver interface with a permanently pending future; it performs no DNS query and returns no address/TCP connection.

The parent waits for evidence that each operation entered the blocked phase, then requests stop. Assertions require completed supervision/reaping within the two-second shutdown budget, the retained Stopped reason, no after-operation continuation marker, no remaining child PID, rejection of later host input, and HTTP/TLS socket closure. A child-only launcher clears proxies and sends Rust test-harness text to stderr; no production endpoint/credential override is added. All addresses are local, and the resolver name uses the reserved .invalid domain with a resolver that never delegates.

These fixtures verify supervisor termination while representative startup work is stalled. They use exact test harnesses calling production helpers, not a live Discord account or a full installed live worker. They do not complete a trusted TLS handshake, test certificate acceptance, or inject a stall into the native OS getaddrinfo call. Successful TLS/live service and actual live network-to-history/reply acceptance remain open; no claim of graceful cleanup inside a killed HTTP/TLS call is made.

## Verify application history without an account

From a developer checkout, run the built app with `--verify-discord-replay` alone. This is an explicit execution check: it installs/enables only the bundled owned replay in a private temporary profile, launches its unchanged Python/native entry point through the real installed runtime, and pumps the actual `StudioExternalMessages` sink and chunk queue. It waits for the normal four-second window and compares persisted external history with app state. No profile path argument is accepted.

The check disables replies, voice and model discovery, invalidates provider/decision routes, and leaves memory intake enabled to verify the external-text boundary. It checks exact original author/text/source identity, host attribution, one external turn, preserved composer draft, unchanged notes/fact candidates/records/generation/status, no active model/picker work, no credential file and successful cleanup/reaping. Success emits one JSON report after the temporary profile has been removed. Existing profiles and default coordination state are unused.

This is a real application-binary→installed native replay→app intake→disk-history check, rather than a recording-sink substitute. Its host target is synthetic/headless; it does not start a renderer, load a VRM, generate a reply or establish a live Discord connection. It complements the prior local-network and installed-process fixtures. Actual live network-to-history/reply, rendered speech/gesture and voice/media acceptance remain open.

### Application media intake

`extension_audio_intake.rs` owns turn storage and a single pending ASR job. Each frame derives audio authority only from enabled, active, persistent installed processes with both grants, excluding manual tests and one-shot hooks. Host session/process/origin, loaded avatar and installation/settings/credential revision pin the route. Turning listening off, losing authority, or changing the ASR configuration/session key discards turns and pending jobs. Pending results expire after45 seconds; a blocked worker may retain the single slot until the existing HTTP timeout. No provider work occurs for Start/Frame, and Finish reserves capacity before consuming a turn. Cancel can invalidate an already submitted turn.

A successful result is validated without truncation and offered as external chat with original participant identity and a fresh host-owned audio source ID. Existing chunking, source-revision checks, reply opt-in and authored-user memory exclusion apply. Invalid or oversized recognized text is rejected with a fixed notice. The source receives immediate record-admission receipts and private `audio.input.finished` completion metadata; asynchronous failures also appear as fixed host notices. No bundled adapter requests the audio grant yet. Localhost fixture tests exercise real WAV upload through the configured ASR adapter, exact participant/text retention and dropping a revoked in-flight result. Real call receive, echo suppression, outgoing audio and a user-confirmed call remain open.

### Private audio completion receipts

After an admitted Finish, `audio.input.finished` carries the original `target`, `turn_id`, and an `outcome`: `queued` means recognized text entered the external candidate queue, `failed` means ASR failed, `rejected` means the recognized text or incoming offer was refused, and `cancelled` means pending work was invalidated. It contains no recognized text, participant details or provider error body. Queued does not prove history persistence, selection, reply generation or call playback.

Receipts route only to the original active process session/generation and origin, with both audio-transcription and message-delivery grants still present. Lifecycle observation is not required; receipts are neither broadcasts nor hook triggers. A replacement process never inherits them. Disconnect or revoked grants can prevent delivery, so receipt absence is an uncertain outcome and must not trigger automatic turn replay. Host cancellation retains the original target as metadata even if the avatar changed.

The application reserves room for at most eight completion records and one pending job. When completions are full, Finish returns Busy before consuming audio. Explicit Cancel, service/key changes, source/target loss and pending deadlines create Cancelled metadata for submitted work; unfinished Start/Frame buffers still have ordinary admission/expiry semantics. Localhost tests cover ASR success/failure, unsupported text, source revocation and explicit cancellation. The installed fixture verifies the private Queued event without lifecycle permission and rejects stale session/process/source routes.
