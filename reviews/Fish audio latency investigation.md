# Startup waits explain Fish audio delays

Your recollection that it was faster is plausible. Saved runs include substantially quicker responses, and our benchmark and app do not always start their clocks—or open their connections—at the same point. **We found real startup costs in the client, but no evidence establishing a Fish service regression.** A credible public WebSocket benchmark reports 141 ms, yet it measures text-to-first-compressed-audio packet after connecting; our quoted figures measure Send-to-decoded-audio readiness. The app also waits for text before opening WebSocket, while some earlier benchmarks connected alongside chat generation. Changing defaults alone does not explain or fix a six-second response. This investigation used public documentation, source inspection and saved results; it made no live requests, builds or new benchmarks.

## The 150–200 ms claim measures less

Vapi’s maintainer reports **141 ms median over 50 S2.1-Pro WebSocket trials**. Their transport measures connection establishment separately, starts the audio clock after sending text, and stops at the first nonempty MP3 audio event. It uses balanced latency, a stock voice without a reference ID, and immediately sends text, flush and stop. It excludes chat generation, handshake time, decoding and speaker playback. That supports a real low-latency target, but does not establish equivalent end-to-end app performance. Jard’s exact timer, model and voice remain unknown. ([Maintainer report](https://github.com/VapiAI/humanness-index/issues/2), [transport source](https://github.com/VapiAI/humanness-index/blob/main/src/pipeline/transports/fish.ts))

Our saved fixed-text Drama 3 tests recorded **617 ms minimum / 630 ms median HTTP**, versus **1,032 ms minimum / 1,034 ms median WebSocket**, with three samples per mode. The latest DeepSeek app-path tests recorded **965 / 981 ms HTTP** and **1,383 / 1,496 ms WebSocket** minimum/median from Send; first-text medians were 290 and 354 ms. These small batches are workload-specific, and the generated texts differ. Neither experiment measures physical speaker onset. ([Fixed-text results](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/benchmarks/speech-drama-vs-s21.json), [app-path results](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/benchmarks/pipeline-sentence-sse-low.json))

## Connection setup already consumes about 0.6 seconds

In five saved instrumented Drama 3 WebSocket calls, the socket became ready **611–631 ms after session start**. First-flush-to-first-wire-audio took another **423–444 ms**, median 427 ms. That latter interval includes transit and Fish processing; it is not isolated server inference. The available fields cannot separate proxy negotiation, TCP, TLS and WebSocket upgrade. Required proxy routing must remain intact. ([Instrumented results](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/benchmarks/pipeline-deepseek-instrumented.json))

Production opens the socket only after nonempty filtered speech text exists, losing the opportunity to overlap setup with the earlier LLM wait. Earlier direct benchmarks opened alongside chat generation; explicit prewarm runs opened before the Send clock. One prewarmed sample reached decoded audio 701 ms after Send, but the excluded one-second preparation makes that 1,701 ms from preparation start. These are different startup policies, not proof that the service slowed down. ([Production gate](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/src/studio.rs:485), [benchmark policy](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/examples/bench_pipeline.rs:752), [prewarm results](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/benchmarks/pipeline-deepseek-prewarm.json))

## The client adds text and audio readiness gates

HTTP/SSE speech waits for a sentence boundary after at least **40 characters**, a 300-character cap, or reply completion. A short initial sentence can therefore wait unnecessarily for more text. WebSocket explicitly flushes after sentence punctuation at ten characters, whitespace at 24, clause punctuation at 44, or a hard 68-character cap. Fish documents buffering incoming text and provides flush to force synthesis. ([HTTP grouping](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/src/reply_speech.rs:175), [WebSocket grouping](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/src/fish_ws.rs:85), [Fish WebSocket API](https://docs.fish.audio/api-reference/endpoint/websocket/tts-live))

All streaming paths wait for **180 ms worth of decoded PCM**, or EOF for shorter audio, before announcing playback readiness. This is a media-duration threshold, **not a fixed 180 ms wall-clock sleep**: a sufficiently large packet can satisfy it immediately. Bevy update, audio scheduling and the device add further unmeasured delay. HTTP and SSE also construct a new reqwest client for each request, preventing connection-pool reuse across utterances/chunks. ([Decoder gate](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/src/voice_stream.rs:487), [HTTP client](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/src/voice.rs:654), [SSE client](/home/subsect/Documents/Codex/2026-10-17/ma/outputs/waifu-studio/src/fish_live.rs:391))

## The API has options, not a guaranteed magic switch

We already serialize latency, chunk lengths, conditioning and reference ID; the app does not upload reference audio each turn. Canonical documentation accepts low, normal and balanced latency, while the streaming guide calls balanced fastest and the Python SDK defaults to balanced. A public transport author found balanced about 18 ms faster than low locally. Consequently **“low” does not prove the lowest actual latency**. Drama 3 has no documented comparable TTFA guarantee, and S2.1’s result cannot simply transfer to it. ([Canonical API](https://docs.fish.audio/api-reference/endpoint/openapi-v1/text-to-speech), [streaming guidance](https://docs.fish.audio/features/realtime-streaming), [comparison](https://github.com/VapiAI/humanness-index/pull/3), [Drama 3](https://docs.fish.audio/features/text-to-speech/drama-3))

The next fixes should follow evidence: **first expose separate connect, text-ready, flush, first-wire, decoded-ready and playback-start times in the real app**. Then reuse HTTP clients, overlap WebSocket connection establishment with generation where safe, and permit a shorter first HTTP phrase. Only afterward tune the PCM startup threshold against underruns. WebSocket finish closes the connection, so persistent reuse cannot assume one finished socket supports future turns; prewarming needs lifecycle and cancellation checks. These are ranked optimization candidates, not measured savings.

## What the evidence changes

There is no basis to dismiss your remembered faster behavior. Different LLMs, earlier connection opening and different timing endpoints provide concrete explanations worth checking. There is equally no evidence yet that Fish itself regressed or that a hidden API setting accounts for six seconds. The useful next step is to identify which interval expands in an actual slow turn, then remove that specific wait rather than repeat model benchmarks or promise that a default change fixes playback.
