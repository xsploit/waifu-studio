# Hikari: MotionBricks, VRM, retargeting, and collision

Research and local inspection, 2026-10-30. This is a proposed direction, not a claim that motion or collision has been fixed.

## Conclusion

There is no evidence that the VRM container is the fundamental obstacle. Keep Hikari as a VRM for the next experiment and treat motion generation, retargeting, body collision, secondary motion, and rendering as separate systems. Each needs to be checked on the actual character. Switching her to generic glTF, FBX, or another engine might provide different tools, but does not by itself fix retargeting, skin weights, or intersection. VRM is a glTF-based avatar format with humanoid and other avatar-specific data; a replacement would need equivalents for any lost expressions, materials, and secondary-motion configuration. [VRM overview](https://vrm.dev/en/vrm/vrm_about/)

## How MotionBricks would animate Hikari

The SOMA model takes four recent skeleton poses and one to four target poses. It generates short in-between motion segments; the official runtime chains them using the poses actually displayed. Its normal output is 18–58 usable frames at 30 Hz, or approximately 0.6–1.9 seconds. NVIDIA's Smart Primitives are authored arrangements of poses and interaction information, not a text model and not automatic collision detection. A clip, an authored pose library, or an offline generator such as Kimodo can provide target poses. The companion's decision layer would choose the behavior and appropriate targets. [NVIDIA runtime API](https://github.com/NVlabs/motionbricks/blob/main/docs/runtime_api.md), [NVIDIA repository](https://github.com/NVlabs/motionbricks)

For example: a decision selects a friendly speaking gesture; select an approved target pose with arms clear of Hikari's clothes; generate a transition from the current pose; retarget to Hikari; apply any proven, constrained corrections; then play the gesture or a speaking idle. Interpolate 30 Hz poses for a higher-rate renderer. Gaze and expression stay controlled by Hikari's face system. Target selection, interruption, transitions, and quality checks all need implementation. A taskbar-sit interaction also needs a taskbar-aware seat position and a pose that fits Hikari; the generator does not discover the taskbar by itself.

NVIDIA also provides optional hand/foot IK pins near a target and foot-contact predictions. The uncut human UE5 demo claims no collision detection, foot-locking, blending, or hand-authored transitions. That demonstration is not proof that every motion or character is collision-free. The SOMA model card says scene geometry and text are not inputs and collision avoidance is not guaranteed. The G1 robot model is a different checkpoint and output representation. [Project demo](https://nvlabs.github.io/motionbricks/), [SOMA model card](https://github.com/NVlabs/motionbricks/blob/main/docs/soma_model.md)

## What Hikari already contains

Inspection of `assets/characters/models/81453f3567d8-hikari-wardrobe.vrm` shows a VRM 0 avatar with 22 secondary-animation groups and 18 collider groups. Its two skirt spring groups explicitly reference collider groups attached to both hands, both upper legs, and the hips; there are also sleeve and hair springs. The skirt has some authored response to nearby hands. This is metadata inspection, not proof that the active runtime shows the intended results for every pose. The Waifu Studio loader and spring solver have code for VRM 0 collider groups and sphere collision; inspect the loaded values and actual live behavior before drawing conclusions about this particular avatar.

Spring-bone collision moves spring joints against simplified colliders, not all mesh vertices against all other mesh vertices. It does not automatically constrain the animated forearm to stay outside the skirt or guarantee that the fabric surface follows its spring joints without intersections. A hand can therefore penetrate despite the authored setup, and body, sleeve, and skirt intersections require separate tests. [VRM spring-bone algorithm](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_springBone-1.0/README.md)

The existing arm-clearance code approximates body shape and adjusts arm pose when enabled. Previous visual reviews found that it could create unnatural shoulders and elbows. Do not use improved clearance metrics as the acceptance criterion if the character looks broken. Correct only enough to preserve intended motion, normal anatomy, and continuity, and reject/fall back from poses that cannot be safely corrected.

## Retargeting is an unverified part of the current prototype

The current offline preview maps 22 SOMA joints explicitly onto VRM humanoid bones and excludes eyes and jaw. Its special map is important: SOMA `LeftLeg` is the upper leg, while a generic Mixamo naming convention may use that name for the lower leg. The exporter preserves the source rest hierarchy but writes rotation tracks only for mapped joints. Extra source joints and the impact of omitted animated intermediate joints need explicit testing; no claim is made that this caused the observed hand/skirt intersections. Source and target proportions, rest pose, bone axes, coordinate systems, and shoulder/elbow/wrist orientation all affect the result.

VRMA expects a VRM T-pose in the rest hierarchy and specifies how humanoid pose data is mapped. Confirm that the experimental export conforms rather than assuming that putting an arbitrary source skeleton into a VRMA is sufficient. The specification separates eye gaze from humanoid eye animation, and Waifu Studio's body animation code explicitly excludes eye bones. [VRMA specification](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm_animation-1.0/README.md)

The existing MotionBricks preview generated two chained segments and rendered Hikari from front and side at 30 FPS with the arm guard off. Some hands/fingers appear to enter or disappear behind the skirt, so this sample is not accepted as collision-free. A 2D image alone cannot resolve every depth ambiguity. We have not rendered the exact same generated poses on the SOMA source alongside Hikari, so we cannot yet attribute the artifact to the generator, export/retargeting, avatar geometry, or combinations of them. See [the earlier local evaluation](motionbricks-tensorrt-evaluation-2026-10-30.md).

## Recommended experiment and acceptance gate

1. Render the exact same generated frames on the original SOMA rig and Hikari, synchronized, from front, side, and rear. Include a neutral pose, arms at side, talking gestures, turning, and a seated pose. Overlay joint axes, arm landmarks, visible collision proxies, and the skinned garment; verify source and target rest poses and mapping. Check missed parent motion and unit/up-axis conversion. Preserve the generated sequence for repeatable comparisons.
2. Compare Hikari with guard off and with carefully constrained corrections. Fit simple avatar-specific torso, arm, and skirt clearance proxies to the animated character; use joint limits and smooth changes, not a large one-step shoulder rotation. Resolve hand/forearm contact using a solver that preserves the intended gesture. If fitting or correction is unreliable, reject that segment and use an approved clip rather than showing a broken arm.
3. Test skirt and sleeve springs separately with the actual loaded colliders, then inspect the final rendered garment. Add more detailed garment/body collision or improve the asset when the cheap proxy approach cannot meet the quality bar. Do not promise perfect mesh-level contact from springs or capsules alone.
4. Review full-motion multi-angle frames, transitions and live desktop use for recognizable movement, no visible clipping, no broken shoulders/elbows, stable feet, and independently controlled eyes. Keep a curated approved baseline while work continues; do not label an entire animation library fixed after a smoke test.
5. Only after motion quality passes, connect an optional long-lived TensorRT worker to Waifu Studio and expose motion selection to the decision system. Measure GPU memory, process RAM, CPU, render frame times, and latency concurrently with the app; support lazy loading/unloading and a non-NVIDIA/disabled fallback. Avoid making AI chat wait on pose generation. Design any worker protocol and process lifetime explicitly for Windows and Linux.

## Hardware and redistribution evidence

On the local RTX 5060 Ti, Windows TensorRT produced two offline test generations. The cached run's two synchronized calls were about 30 ms and 2.4 ms; two calls are not a performance benchmark. First-time build used substantial RAM. Linux under WSL saw the GPU, but the build was terminated before generating output; native Linux GPU operation remains unverified. NVIDIA's reference runtime requires an NVIDIA GPU; its models and sample motion data have separate terms. The sample-derived preview is a local test, not a release asset. [NVIDIA repository and terms](https://github.com/NVlabs/motionbricks), [sample-data terms](https://github.com/NVlabs/motionbricks/blob/main/assets/motions/LICENSE.txt)
